[초안 · 최종 화면 동결 뒤 버튼 이름과 숫자를 다시 확인할 것]

[00:00–00:25 · Scenario Lab 첫 화면]

3D Ledger가 새로 바뀌었습니다.

이제 질문은 단순히 3D SRAM에 몇 퍼센트가 들어가는지가 아닙니다. weight, KV, state 가운데 어떤 바이트를 가까이 남겼을 때, 다음 스텝의 HBM 이동이 실제로 가장 많이 줄어드는지를 비교합니다.

[00:25–01:05 · 전체 시스템, 짧은 문맥에서 긴 문맥으로 전환]

먼저 저장량과 이동량을 나눠 보겠습니다.

HBM 막대는 모델이 오래 들고 있는 원본 데이터의 크기입니다. 가까운 메모리 막대는 그중 선택해 둔 사본입니다. 사본이 생겨도 HBM의 원본이 자동으로 사라지는 것은 아닙니다.

짧은 문맥에서는 공유하는 weight 읽기가 상대적으로 큽니다. 문맥과 배치가 커지면 KV가 자라고, 한 스텝에서 다시 읽어야 할 양도 커집니다. 반면 recurrent state는 크기가 고정돼도 매 스텝 읽고 다시 쓸 수 있습니다.

그래서 저장 공간의 몇 퍼센트를 덮는가와, 한 스텝에서 몇 바이트의 이동을 없애는가는 같은 숫자가 아닙니다.

[01:05–01:50 · state, sliding, MoE, MLA 프리셋]

모델 구조가 바뀌면 판단 단위도 달라집니다.

하이브리드 모델의 state는 읽기와 쓰기를 함께 봐야 합니다. 슬라이딩 attention은 창 밖의 오래된 KV를 계속 보존할 이유가 없습니다. MoE는 모든 전문가가 아니라 지금 자주 선택되는 expert page를 봐야 하고, MLA는 펼친 MHA KV가 아니라 압축된 latent KV 크기로 계산해야 합니다.

Ledger의 정책은 모델 이름에 고정된 정답표가 아닙니다. 객체의 크기, 수명, 다음 접근, 읽기와 쓰기, 요청 간 공유를 같은 단위로 비교하는 출발점입니다.

[01:50–02:35 · 추가 3D SRAM과 기존 L2 분할, capacity cliff]

하드웨어 방식도 구분해야 합니다.

추가 3D SRAM은 기존 L2를 빼앗지 않는 새 공간이라는 설계 가정입니다. 반면 기존 L2의 일부를 보호 영역으로 예약하는 B200 실험은, 보호한 만큼 일반 캐시가 쓸 공간이 줄어듭니다.

그래서 자주 쓰는 데이터를 남겨도 항상 이기는 것은 아닙니다. 객체를 충분히 덮지 못하거나 다른 유용한 캐시 데이터를 밀어내면 결과가 오히려 느려질 수 있습니다. 화면의 capacity cliff가 바로 이 입장 거부 조건을 보여 줍니다.

[02:35–03:50 · 한 요청 따라가기, cold → reuse → dirty]

이번에는 한 데이터 조각을 따라가 보겠습니다.

처음 읽는 조각은 먼저 L2에 있는지 확인합니다. 미스가 나면 HBM에서 가져와 L2에 사본을 채우고, 다시 연산부로 전달합니다. 같은 조각을 다시 읽으면 L2 적중으로 HBM 읽기를 피할 수 있습니다.

하지만 캐시가 가득 찬 상태에서 새 조각이 들어오면 오래 쓰지 않은 조각이 교체됩니다.

수정된 state 조각은 더 복잡합니다. L2에서 값을 바꾼 뒤 곧바로 HBM에 쓰는 것이 아니라, dirty 상태로 남아 있다가 교체될 때 HBM으로 되쓸 수 있습니다. 그래서 배치 정책은 읽기 절감뿐 아니라 fill, eviction, write-back 비용까지 함께 계산해야 합니다.

여기의 A와 B는 설명용 16 MiB 타일입니다. 완전 연관 LRU와 write-back을 가정한 교육용 모델이며, 실제 B200의 128바이트 cache line이나 실제 주소 추적을 재현한 화면은 아닙니다.

[03:50–04:45 · B200 배치 검증, 근거 펼치기]

이 정책 원리는 실제 B200의 persisting L2를 이용한 대리 실험으로 확인했습니다.

동일한 64 MiB weight, KV, state를 같은 커널과 접근 순서에서 비교했을 때, 두 B200을 합친 기하평균은 weight 1.0554배, KV 1.0562배, state 1.1099배였습니다. state는 서른여섯 개 matched cell에서 모두 1위였습니다.

크기와 layer slice를 바꾼 열여덟 조건, 천육백이십 trial에서는 validation 오류가 없었습니다. 동시에 큰 객체를 일부만 보호한 구간에서는 이득이 뒤집히는 실패 사례도 나왔습니다.

이 숫자는 end-to-end LLM 속도 향상이 아닙니다. 같은 크기의 합성 객체를 기존 B200 캐시에 배치해, 순위와 capacity cliff를 확인한 통제 실험입니다.

[04:45–05:25 · replay.html B200 기록 재생]

기존 3D 재생판의 역할도 남아 있습니다.

여기서 B200 녹화는 토큰이 생성된 실제 시간축과 답 글자를 제공합니다. 그 시간의 weight, KV, state 저장량과 논리 접근량은 모델 구조식으로 다시 계산합니다. 움직이는 구슬은 실제 cache line을 촬영한 것이 아니라, 계산한 객체별 접근을 설명하는 표본입니다.

따라서 실측 시간과 계산한 이동 경로를 같은 증거로 섞지 않습니다. 원장 모델과 서버 모델이 다르면 실측을 숨기고, 일치할 때만 함께 보여 주는 이유도 같습니다.

[05:25–06:00 · 근거와 한계]

마지막으로 초록 실측, 파란 유도, 노란 가정을 구분해 읽어 주세요.

현재 닫힌 결론은 어떤 객체를 남길지 정하는 정책 원리와 B200 캐시 대리 검증입니다. 아직 제작된 3D SRAM의 전력, 열, 면적, 지연을 잰 것이 아니고, 실제 serving engine에서 end-to-end 속도 향상을 증명한 것도 아닙니다.

Ledger3D는 이 미확정 부분을 숨기지 않고, 어떤 입력과 비용이 추가되어야 다음 설계 결정을 할 수 있는지 원장으로 남깁니다.
