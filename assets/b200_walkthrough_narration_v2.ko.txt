[01 · Scenario Lab 첫 화면]

3D Ledger가 새로 바뀌었습니다.

이제 질문은 단순히 3D SRAM에 몇 퍼센트가 들어가는지가 아닙니다. weight, KV, state 가운데 어떤 바이트를 가까이 남겼을 때, 다음 스텝의 HBM 이동이 실제로 가장 많이 줄어드는지를 비교합니다.

[02 · 전체 시스템, 짧은 문맥에서 긴 문맥으로]

먼저 저장량과 이동량을 나눠 보겠습니다.

HBM 막대는 모델 구조로 계산한 원본 크기이고, 엔진이 할당한 양을 덤프한 값이 아닙니다. 가까운 메모리 막대는 그중 선택해 둔 사본입니다. 사본이 생겨도 HBM의 원본이 자동으로 사라지는 것은 아닙니다.

짧은 문맥에서는 전체 읽기 양으로 보면 공유 weight가 큽니다. 하지만 한 바이트를 남겼을 때의 절감 가치로 따지면 화면의 우선순위는 KV가 먼저입니다. 절대 트래픽과 바이트당 가치를 구분해서 읽어야 합니다.

문맥과 배치가 커지면 KV가 자라고, 한 스텝에서 다시 읽어야 할 양도 커집니다. 반면 recurrent state는 문맥이 길어져도 크기가 늘지 않습니다. 대신 배치에 비례해 커지고, 매 스텝 읽고 다시 씁니다.

그래서 저장 공간의 몇 퍼센트를 덮는가와, 한 스텝에서 몇 바이트의 이동을 없애는가는 같은 숫자가 아닙니다.

[03 · 하이브리드, 슬라이딩, MoE, MLA]

모델 구조가 바뀌면 판단 단위도 달라집니다.

하이브리드 모델의 state는 읽기와 쓰기를 함께 봐야 합니다. 슬라이딩 attention은 창 밖의 오래된 KV를 계속 보존할 이유가 없습니다. MoE는 모든 전문가가 아니라 자주 선택되는 expert page를 봐야 하고, MLA는 펼친 MHA KV가 아니라 압축된 latent KV 크기로 계산해야 합니다. 다만 화면의 MoE 값은 균등 라우팅을 가정한 합집합이지 실제 선택 기록이 아닙니다.

Ledger의 정책은 모델 이름에 고정된 정답표가 아닙니다. 객체의 크기, 수명, 다음 접근, 읽기와 쓰기, 요청 간 공유를 같은 자리에 놓자는 출발점입니다. 지금 화면이 계산하는 값은 상주 바이트당 읽기와 쓰기뿐입니다.

[04 · 추가 3D SRAM과 기존 L2 분할]

하드웨어 방식도 구분해야 합니다.

추가 3D SRAM은 기존 L2를 빼앗지 않는 새 공간이라는 설계 가정입니다. 반면 기존 L2의 일부를 persisting 예약 영역으로 떼어 내는 B200 실험은 같은 물리 캐시를 나눠 씁니다. 이 예약은 캐시 라인을 고정하지 않는 힌트이고, 남은 예약 용량은 일반 접근이 그대로 씁니다.

그래서 결과에는 영역을 떼어 낸 대가와 객체를 지목해 되찾는 이득이 겹쳐 있습니다.

육십사 메비바이트에서는 영역만 예약하면 사 점 팔 퍼센트 손해지만, state를 지목하면 일 점 일육사 배를 되찾아 최종 일 점 일영팔 배가 됩니다. 이백오십육 메비바이트에서는 대가가 육 점 이 퍼센트인데 지목 효과가 영 점 구구구구 배, 아무것도 되찾지 못합니다. 화면의 캐시 분할 역효과 프리셋이 이 상태입니다.

즉 느려진 원인은 엉뚱한 객체를 지목해서가 아니라 잘라낸 비용만 남았기 때문입니다. 예약이 객체의 팔십이 점 사 퍼센트를 덮은 구십육 메비바이트는 쉰네 비교 중 쉰세 번 이득이었고, 삼십 점 구 퍼센트뿐이던 이백오십육 메비바이트는 쉰네 비교 모두에서 이득이 없었습니다. 이 값들은 이 커널의 교정점이지 보편 임계값이나 캐시 적중률이 아닙니다.

[05 · 한 요청 따라가기]

이번에는 한 데이터 조각을 따라가 보겠습니다.

처음 읽는 조각은 먼저 L2에 있는지 확인합니다. 미스가 나면 HBM에서 가져와 L2에 사본을 채우고, 다시 연산부로 전달합니다. 같은 조각을 다시 읽으면 L2 적중으로 HBM 읽기를 피할 수 있습니다.

캐시가 가득 차면 오래 쓰지 않은 조각이 교체됩니다.

수정된 state 조각은 곧바로 HBM에 쓰지 않고, dirty로 남아 있다가 교체될 때 되씁니다. 그래서 배치 판단에는 fill과 eviction, 되쓰기 비용도 들어가야 합니다. 다만 이 화면의 배치 점수는 상주 바이트당 읽기와 쓰기만 세고 그 셋은 아직 빠져 있습니다.

여기의 A와 B는 설명용 십육 메비바이트 타일이고, 완전 연관 LRU와 write-back을 가정한 교육용 모델입니다. 실제 cache line이나 주소 추적이 아닙니다. dirty A도 weight 갱신이 아니라 수정 가능한 state의 예시입니다.

표시된 HBM 초당 팔 테라바이트와 사백 나노초, L2 초당 삼십 테라바이트와 백 나노초, SRAM 초당 이십 테라바이트와 오십 나노초는 편집 가능한 설명용 가정입니다. 동시 요청과 전송 겹침, 실제 연산, 종료 flush는 포함하지 않습니다. 최초 적재는 근접 메모리 상주 사례에서 단계 0으로 재생하고, 같은 양 비교에서만 뺍니다.

[06 · B200 배치 검증]

이 정책 원리는 실제 B200의 persisting L2를 이용한 대리 실험으로 확인했습니다.

정확히 육천칠백십만 천육백구십육 바이트로 정렬한 동일 객체를 같은 커널과 접근 순서에서 비교했습니다. 두 B200을 합친 기하평균은 weight 일 점 영오오사 배, KV 일 점 영오육이 배, state 일 점 일영구구 배였습니다. state는 서른여섯 개 matched cell에서 모두 일 위였습니다.

크기와 layer slice를 바꾼 열여덟 조건, 천육백이십 trial에서는 validation 오류가 없었습니다. 동시에 큰 객체를 일부만 보호한 구간에서는 이득이 뒤집히는 실패 사례도 나왔습니다.

이 숫자는 end-to-end LLM 속도 향상이 아닙니다. 같은 크기의 합성 객체를 기존 B200 캐시에 배치해, 순위와 capacity cliff를 확인한 통제 실험입니다. 추가 3D SRAM 실리콘의 측정값도 아닙니다.

[07 · B200 기록 재생]

기존 3D 재생판의 역할도 남아 있습니다.

여기서 B200 녹화는 토큰이 생성된 실제 시간축과 답 글자를 제공합니다. 그 시간의 weight, KV, state 저장량과 논리 접근량은 모델 구조식으로 다시 계산합니다. 움직이는 구슬은 실제 cache line을 촬영한 것이 아니라, 계산한 객체별 접근을 설명하는 표본입니다.

따라서 실측 시간과 계산한 이동 경로를 같은 증거로 섞지 않습니다. 원장 모델과 서버 모델이 다르면 실측을 숨기고, 일치할 때만 함께 보여 주는 이유도 같습니다.

[08 · 근거와 한계]

마지막으로 화면의 딱지를 구분해 읽어 주세요. 초록은 측정, 파랑은 유도, 밝은 회색은 제조사 발표값, 노랑은 가정입니다.

현재 닫힌 결론은 어떤 객체를 남길지 정하는 정책 원리와 B200 캐시 대리 검증입니다. 아직 제작된 3D SRAM의 전력, 열, 면적, 지연을 잰 것이 아니고, 실제 serving engine에서 end-to-end 속도 향상을 증명한 것도 아닙니다.

화면에서 회색 HBM 영역은 측정된 빈 공간이 아니라 이 설명 모델이 다루지 않는 영역입니다. 캐시 사본이 생겨도 HBM 원본은 없어지지 않습니다.

Ledger3D는 이 미확정 부분을 숨기지 않고, 어떤 입력과 비용이 추가되어야 다음 설계 결정을 할 수 있는지 원장으로 남깁니다.
