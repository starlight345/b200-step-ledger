# 비주기 decode 장부에서의 정책 분리, 2026-09-21

`3dsram_closure_20260921`의 재생은 한 스텝을 32회 반복한다. 타일 정체성 집합이 전혀 변하지 않으므로 LIP의 first-fill 보존이 고정 배치와 **원리적으로 구분되지 않는다**(상주 집합 겹침 3149/3151). 이 실험은 그 축을 하나 추가한다. 요청이 도착하고 이탈하며 KV 타일 정체성이 바뀐다.

## 재현

```bash
python3 build_trace.py --steps 128 --batch 8 --mean-len 120
python3 replay_policies.py
python3 make_figure.py
```

`--mean-len`이 회전 손잡이다. 크면 주기에 가깝고 작으면 회전이 빠르다.

## 트레이스

- 층 단위 인터리빙: `for layer: weight[l] 읽기, 각 live 요청의 KV[l] 읽기·쓰기`. **이 순서가 결론을 정한다.** 1차 시도는 32개 층 weight를 먼저 내보내고 KV를 뒤에 두었는데, 그러면 first-fill이 자명하게 weight만 잡아 bypass와 managed가 구성비까지 같아지고 회전을 45요청까지 올려도 모든 정책이 18.5%로 붙는다. 음성 결과였고 순서 때문이었다.
- 도착 Poisson, 길이 lognormal(sigma 0.8), 배치 8 목표, 시드 고정. step 0에 미리 채워 정상 상태에서 시작한다.
- weight는 요청 불변, KV는 요청 id로 키가 붙어 도착에 생기고 이탈에 사라진다.

## 정책 다섯

| 정책 | 사다리 | 동작 |
|---|---|---|
| LRU | — | 수요 충전, LRU 교체 |
| LIP | 3단 | 수요 충전, 새 줄이 LRU 자리로 |
| LIP-bypass | 3b단 | 가득 차면 미스 시 비할당. 한 번 채우고 얼림 |
| managed | 4단 | weight만 입장, KV는 거부 |
| managed+KV | 4b단 | weight 고정 후 남는 자리를 KV에 LRU로 |

## 결과

| mean_len | 이탈/스텝 | bypass 정상 | managed 정상 | 델타 |
|---:|---:|---:|---:|---:|
| 10000 | 0.062 | 18.430% | 18.448% | +0.018%p |
| 300 | 0.086 | 17.578% | 18.477% | +0.900%p |
| 120 | 0.133 | 16.451% | 18.532% | +2.081%p |
| 30 | 0.250 | 16.182% | 18.561% | +2.379%p |
| 10 | 0.594 | 16.195% | 18.576% | +2.381%p |

주기 극한에서 0.018%p로 사라지고(기존 재생 재현), 이탈 0.17/스텝부터 **2.38%p에서 포화**한다. managed는 회전과 무관하게 평탄하고 bypass만 떨어진다.

**메커니즘.** 상주 집합 구성이 설명한다. bypass는 도착 순서대로 얼려 용량의 **12.2%를 요청 KV에 물고**, 그 요청이 이탈하면 그 타일이 죽은 채 자리를 차지한다. managed는 KV를 입장시키지 않아 **100% live**다. 포화 델타 2.38%p가 죽은 12.2%의 손실과 맞는다.

**`managed+KV`가 결정적이다.** 남는 자리를 KV에 주면 bypass와 소수점 셋째 자리까지 같다. 따라서 **델타는 고정(pinning)이 아니라 입장 판정(admission)에서 온다.**

## 등급과 한계

전부 **trace replay**이며 **합성 장부**다. 실제 서빙 trace가 아니다. ShareGPT나 Azure trace는 회전 분포가 달라 포화 지점과 델타 크기가 움직인다. 하드웨어 캐시 세트 모델이 아니고 HBM 카운터도 아니다. 양쪽 티어 트래픽(읽기와 충전)을 모두 센다.

통계 규약: 정상 상태 = 마지막 스텝, 평균 = 128스텝 평균. 표마다 명시한다.
